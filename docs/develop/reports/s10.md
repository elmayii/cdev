## What was deliberately not built, and why

- **Requirement and user-story lists in the plan.** The planner's first draft had each sprint
  carry ID'd requirements and stories with per-batch coverage, so status could be computed.
  Rejected by the human: sprints and batches already hold the intent in free form, and a
  formalized list must be kept current while a feature is still being discovered — that
  maintenance is what drifts. In doc 07's terms it restates the plan (singularity) where field
  rule 4 says derive on read. **The plan's format did not change**; neither did the execution
  loop. The rigor went into the reader.
- **Isolation machinery for status** (running it in a fresh subagent so the conversation
  cannot leak into it). Rejected by the human: status is a read operation inside the
  conversation; CDev is a procedure and does not guard the human against their own use of
  context.
- **A workspace (multi-repo) sandbox fixture.** Not built (clarity map: ABSENT). A recorded
  field exercise by the human stands in — protocol §4, local line.
- **A written threshold for "what counts as a gap".** Left to the planner's judgment, held
  conservatively. The cost showed up at once — see below.

## What the exercises taught

- **The baseline asked too.** `main`'s planner is not silent: it asked one round up front, then
  wrote four batches in one go and reported five assumptions "the human has NOT seen". The
  rule does not add questions so much as move them to where the decision is taken, and turn
  unseen assumptions into asked ones.
- **Judgment varies between runs.** The attended planner asked what "the same URL" means; the
  unattended one judged it non-blocking and wrote that batch `READY` with the question
  recorded as open. The RFC's Cost section names exactly this. If field use shows decisions
  still being swallowed, that is the next RFC.
- **`cdev-status` had three defects in its first text**, all found by running it, none by
  reading it: working rules of the repo counted as non-functional requirements (4 of 8 rows);
  an ambiguity about unverified items that one run resolved by giving every axis two figures;
  statuses of ~1,100 words. Fixed and re-exercised; the brevity fix only partly worked.
- **The not-derivable clause took four attempts**, and the fault was mine three times: two
  fixtures that carried the very signal the clause assumed absent, and one whose commit
  message announced the answer to the agent under test. In none of the four did the skill
  invent a requirement — not even input sanitising, for an HTML import feature.
- **Both hand-made fixtures contained a `DONE` batch with no work behind it** — unplanted.
  Every planner run stopped to report it before planning; every status run flagged the
  plan↔handoff↔git disagreement and resolved nothing. The rules held on flaws nobody staged.

## What the field exercise taught (2026-09-20, run by the agent on clones of a real workspace)

- **Both multi-repo skills have now been seen running**, on real data: the planner asked per
  SYSTEM_BATCH before writing, followed the pointer, raised system-level and permission
  decisions, and pushed back on an answer that collided with a repository's local protocol;
  the status led with local truth — the workspace plan said 3 of 8 closed, the repositories 7
  of 8.
- **A status can cost as much as a batch.** The first run fanned out to three subagents and
  died on the usage limit at ~8 USD with nothing delivered. "Read narrowly" brought it to
  ~4 USD and 5.5 minutes — and then over-corrected: the status stopped opening contracts,
  decisions and local handoffs, and said so in its own method note. Fixed to "slices, never
  fewer sources"; that last wording is proven on a fixture only.
- **The honesty of the method note is what caught the over-correction.** A status that names
  what it did not read can be audited; one that does not cannot.

## Contract delta for consumers (installed copies, from 0.2.0)

- Planner runs with a human present now **ask before each batch**. A launch that used to
  produce a plan in one pass will stop for answers.
- An unattended loop that invokes a planner can now find `BLOCKED` batches where it used to
  find `READY` ones.
- Two new commands; nothing removed, no plan format change, no template change —
  repositories conditioned under 0.1.x need no re-conditioning.
